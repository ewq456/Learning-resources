## 一、为什么要用Makefile进行多个.C文件的编译

1. 一般我们在进行项目开发的时候，会建立工程，下面有许多目录，不同目录下又有许多.C文件，这事就需要联合编译了。
2. 我们自己手动编译的话，多个程序文件交织在一起，会出现不同文件资源之间的依赖与被依赖关系。那么在编译的时候就会出现问题：必须先解决被依赖项，在解决依赖项。
3. 在这种情况下，我们进行手动编译的话，将会变得异常困难，首先我们必须记住依赖关系，才能知道编译顺序，其次每一次都要执行非常多的gcc编译命令才能完成最终的编译目标(gcc中还带有许多参数呢)。
4. 这时就得用Makefile，Makefile是工程管理的有效工具，用脚本语言进行编写。

## 二、Makefile的使用规则

- 使用命令：make test
- ./test (test就是你最终生成的目标文件)
- make：只修改你新改动的文件

Makefile中的书写规则：目标... : [依赖项...]、[[@]命令]

1. []中为可写可不写的内容。
2. @符号:命令在终端上出现的关闭符号。
3. 命令前必须有一个tab符号。

Makefile中可以定义变量，好处：减少书写规则；变量的使用格式：${变量名称}。

自动变量：

命令|解释
|:--|:--
$@|代表规则里的目标文件
$^|代表规则里所有依赖文件
$<|代表规则里第一个依赖文件
%.o : %.c|所有的.o文件均一一对应依赖与其后的.c文件(模式规则)

注意：

1. Makefile当中出现.PHONY:clean 意思是，当前目录下也有clean文件时,执行Makefile中的命令clean。
2. 当其中有确定规则时，执行确定规则的命令。

## 四、gdb的使用

### 1、命令

- gcc -g test.c -o test   （-g是调试程序必须用的参数）
- gdb -q test      (-q跳过提示，直接调试) (test要调试的目标文件)
- start    进入调试
- s和n: s表示遇到函数，进入函数，跳转到函数进行调试；n表示不进入函数，继续往下调试。

### 2、设断点

- b  行数
- run : 此时将跳转到该行执行
- 删除断点   d  n(n不是行数，表示将第几个断点删除)
- 查看断点   info  b

### 3、一些输出

- 打印/格式  相应的量
- p/x str    p/c *str   p/d str ......可以查看相应的地址，值，字符...
- 离开gdb调试：q

### Makefile核心语法

```makefile
目标: 依赖
	命令
```

```makefile
# 示例
app: main.o foo.o bar.o
	gcc -o app main.o foo.o bar.o

main.o: main.c
	gcc -c main.c

foo.o: foo.c
	gcc -c foo.c

clean:
	rm -f *.o app
```

# git 常识

## Git里有四个区域很重要

- HEAD、Index、Working Directory
- Git的所有操作实际上是在操作这三个区域的状态（或内容）

- ```js
  + workspace/Working Directory：工作区，就是平时存放项目代码的地方,用户操作区域(就是当前的文件夹)
  
  + Index/Stage：暂存区，用于临时存放你的改动，事实上只是一个文件，保存即将提交到文件列表信息，这个区域里的东西才可以被commit
  
  + Repository：仓库区（或版本库），就是安全存放数据的位置，这里面有你提交到所有版本的数据。其中HEAD指向最新放入仓库的版本
  
  + Remote：远程仓库，托管代码的服务器，可以简单的认为是你项目组中一台电脑用于远程数据交换
  
  // 注：HEAD 指向当前分支最近一次commit里的所有snapshot
  	=> HEAD 是当前分支引用的指针，它总是指向某次commit，默认是最后一次的commit。 这表示 HEAD 将是下一次提交的父结点。 通常，可以把 HEAD 看做你的最后一次提交的快照。当然HEAD的指向是可以改变的，比如你提交了commit，切换了仓库，分支，或者回滚了版本，切换了tag等
      => HEAD是指向当前版本的指针，HEAD^表示上个版本，HEAD^^表示上上个版本
  ```
  
  - 

## 文件的四种状态

- ```js
  1) Untracked：未跟踪，此文件在文件夹中但并没有加入到git库，不参与版本控制，通过git add 状态变为Staged。
  
  2) Unmodify：文件已经入库，未修改，即版本库中的文件快照内容与文件夹中完全一致，这种类型的文件有两种去处
   	=> 如果被修改，而变成Modefied 
  	=> 如果使用 git rm 移出版本库，则成为Untracked文件。
  
  3) Modified：文件已修改，仅仅是修改，并没有进行其他操作，这个文件也有两个去处
  	=> 通过git add可进入暂存Staged状态
  	=> 使用给git checkout 则丢弃修改内容，返回Unmodifiy状态，这个git checkout 即从库中取出文件，覆盖当前修改。
  
  4) Staged：暂存状态，执行git commit 则将修改同步到库中，这时库中的文件和本地文件又变为一致，文件为Unmodify状态，执行git reset HEAD filename取消暂存，文件状态为Modified
  ```

# 常用git指令

## git config

- 主要是用来配置 Git 的相关参数

- ```bash
  # 查看配置信息
  # --local：仓库级，--global：全局级，--system：系统级
  	# local：应用于当前仓库的配置信息
  	# global：应用于当前计算机用户(账户)的配置信息
  	# system：应用于当前计算机的配置信息(当前计算机的每一个用户)
  	# Git会优先使用库级别的配置,再然后是global级别的配置,最后是system级别的配置
  $ git config <--local | --global | --system> -l
  
  # 查看当前生效的配置信息(这个会查看所有的，不加级别参数查看配置，三种等级的配置都会显示)
  $ git config -l
  
  # 编辑配置文件
  # --local：仓库级，--global：全局级，--system：系统级
  $ git config <--local | --global | --system> -e
  
  # 添加配置项
  # --local：仓库级，--global：全局级，--system：系统级
  $ git config <--local | --global | --system> --add <name> <value>
  
  # 获取配置项
  $ git config <--local | --global | --system> --get <name>
  
  # 删除配置项
  $ git config <--local | --global | --system> --unset <name>
  
  # 配置提交记录中的用户信息，配置仓库级别的可以针对不同仓库配置不同的提交用户信息，如果不加参数，默认配置的就是仓库级的
  	# git 不允许匿名提交，需要记录提交记录是由谁完成的，所有需要这两个配置，这两个的值虽然可以随意配置，但是建议配置正确的信息，方便日后管理
  	# 提交信息(这里面就包含提交者的这两项信息)可以在远程仓库中查看，也可以在 git log 的提交日志中查看
  $ git config --global user.name <用户名>
  $ git config --global user.email <邮箱地址>
  
  # 更改Git缓存区的大小
  # 如果提交的内容较大，默认缓存较小，提交会失败
  # 缓存大小单位：B，例如：524288000（500MB）
  $ git config --global http.postBuffer <缓存大小>
  
  # 调用 git status/git diff 命令时以高亮或彩色方式显示改动状态
  $ git config --global color.ui true
  
  # 配置可以缓存密码，默认缓存时间15分钟
  $ git config --global credential.helper cache
  
  # 配置密码的缓存时间
  # 缓存时间单位：秒
  $ git config --global credential.helper 'cache --timeout=<缓存时间>'
  
  # 配置长期存储密码
  $ git config --global credential.helper store
  ```
  
- ```js
  # Git 一共有3个配置文件：
  + 仓库级的配置文件：在仓库的 .git/.gitconfig，该配置文件只对所在的仓库有效。
  + 全局配置文件：Mac 系统在 ~/.gitconfig，Windows 系统在 C:\Users\<用户名>\.gitconfig。
  + 系统级的配置文件：在 Git 的安装目录下（Mac 系统下安装目录在 /usr/local/git）的 etc 文件夹中的 gitconfig
  ```

## git clone

- 将远程仓库的内容克隆拉取到本地的目录中，为克隆的存储库中的每个分支创建远程跟踪分支(使用 `git branch -r` 可见)，并从克隆检出的存储库作为当前活动分支的初始分支

- ```bash
  # 默认在当前目录下创建和版本库名相同的文件夹并下载版本到该文件夹下
  $ git clone <远程仓库的网址>
  
  # 指定本地仓库的目录
  	# 默认是将内容拉取到当前命令行路径下的git仓库同名文件夹内，如果没有则自动生成，如果有则要保证该文件夹是空文件夹
  	# 目录路径可以是相对路径(./ ../),也可以是绝对路径(F:\),也可以直接写目录名(其实也是相对路径，只不过省略了./ , 会在当前命令行的路径下生成指定的目录并拉取内容)
  $ git clone <远程仓库的网址> <本地目录路径>
  
  # -b 指定要克隆的分支，默认的一般是master分支(可以在远程仓库中设置远程仓库的默认分支)
  $ git clone <远程仓库的网址> -b <分支名称> <本地目录路径>
  ```
  
- ```json
  // 关于仓库clone后
  + 会为clone的地址添加一个 origin 仓库别名
  + 会将所有的远程分支进行同步(相当于执行了 git fetch)，- git branch -a - 就能看到远程仓库的所有分支
  + 会创建本地分支和clone拉取的远程分支建立追踪关系，只会创建一个本地分支，分支名和clone的远程分支名相同
  // clone后，拉取其他的远程分支的内容
  1. 使用 -git checkout <远程分支名>- 切换分支，此时因为切换的不是本地分支就会进入 分离头指针 的状态，此时版本指向的是目标远程分支的最新版本(工作区的内容也是对应的远程分支的内容)，此时创建本地分支就是就是以当前的远程分支为基础创建的本地分支，然后切到创建的本地分支上，就完成了指定分支的内容拉取

## git fetch

## git pull

- 从远程仓库获取最新版本并合并到本地。 首先会执行 `git fetch`，然后执行 `git merge`，把获取的分支的 HEAD 合并到当前分支

  - `HEAD是指向当前版本的指针，HEAD^表示上个版本，HEAD^^表示上上个版本。一般回退更多的是到上一个版本`

- ```bash

  # 这是标准形式,指定远程分支与本地分支合并，根据本地分支和远程分支的追踪关系可以进行对应的省略
  # 远程主机名可以是远程仓库地址，也可以是地址的别名
  $ git pull <远程主机名> <远程分支名>:<本地分支名>
  
  # 如果远程分支要与当前分支合并，则冒号后面的部分可以省略，可以简写为
  $ git pull origin <远程分支名>
  # 如果远程分仓库在和当前分支的同名分支则可以省略分支名
  $ git pull origin
  # 如果当前分支只有一个追踪分支，连远程主机名都可以省略()
  $ git pull
  # 如果合并需要采用rebase模式，可以使用–rebase选项
  $ git pull --rebase <远程主机名> <远程分支名>:<本地分支名>
  ```

## git checkout

- 更新工作树中的文件以匹配索引或指定树中的版本。如果没有给出路径 - `git checkout` 还会更新 `HEAD` ，将指定的分支设置为当前分支（也就是切换分支，也是最常用的）

- ```bash
  # 切换到已存在的指定分支
  $ git checkout <分支名称>
  
  # 创建并切换到指定的分支，保留所有的提交记录
  # 等同于 "git branch" 和 "git checkout" 两个命令合并
  $ git checkout -b <分支名称>
  # 强制创建新分支并切换，会覆盖原来存在的同名分支
  $ git checkout -B <分支名称>
  
  # 创建并切换到指定的分支，删除所有的提交记录
  $ git checkout --orphan <分支名称>
  
  # 用于指定版本的文件覆盖工作区中对应的文件
  # <commit>既可以是某一个具体的commit hash值，也可以是某个分支名称，tag名称。不论分支也好，tag也好，它们本质上对应的都是一个commit hash值
  	=> 如果省略 <commit> 会用暂存区的指定文件覆盖工作区中的对应文件
  	=> 不省略的话，则用指定提交中的该文件覆盖暂存区和工作区中的对应文件
  	=> 中间的连字符 -- ，为了避免路径和引用（或提交ID）同名而发生冲突，可以在<paths>前用两个连续的连字符作为分隔
  $ git checkout [<commit>] [--] <文件路径>
  
  # 对工作区进行检查，会提示哪些文件有修改
  $ git checkout
  
  # 在本地创建一个和远程分支同名的分支，并建立追踪关系起来
  $ git checkout --track [remotename]/[branch]
  ```

- ```js
  `# 当 checkout 分支的时候，git做了这么三件事情`
  1) 将HEAD指向那个分支的最后一次commit
  2) 将HEAD指向的commit里所有文件的snapshot替换掉Index区域里原来的内容
  3) 将Index区域里的内容填充到Working Directory里
  // 由分支1切换到分支2时，会将新分支的内容填充到工作区中，会保存你对两个分支共有文件的修改，填充逻辑如下：
  + 对于每一个在分支1但是不在分支2的文件，Git 会删除它们；
  + 对于每一个在分支2但是不在分支1中的文件，Git 会创建它们（用合适的内容）；
  + 对于每一个既在分支1又在分支2的文件，如果版本不同，那么 Git 会更新工作区的文件，使之和分支2的版本匹配
  
  // 注意：用命令git checkout -b <newbranch>创建并切换到一个新分支总是“安全”的：没有文件被创建，也没有文件被删除，也没有文件被更新，索引也没有任何改变
  
  `# 当切换的目标不是分支，而是某个 commit 时`
  + HEAD指针会指向具体的的commit值，进入了“分离头指针”状态，这时查看状态会发现不在任何的分支上，如果要回到分支需要 git checkout <分支名> ,也可以在这个状态上创建新的分支
  + 只有当HEAD切换到某个分支的时候才可以对提交进行跟踪，否则就会进入“分离头指针”的状态
  ```

## git reset

- 还原提交记录

- git reset是会修改版本历史的，他会丢弃掉一些版本历史(还原到的这个版本之后的版本都会被丢弃)

- 如果commit已经被push到远程仓库上了，也就意味着其他开发人员就可能基于这个commit形成了新的commit，这时你去reset，就会造成其他开发人员的提交历史莫名其妙的丢失，或者其他灾难性的后果

- ```bash
  # 重置暂存区，但文件不受影响
  # 相当于将用 "git add" 命令更新到暂存区的内容撤出暂存区，可以指定文件
  # 没有指定 commit ID 则默认为当前 HEAD
  $ git reset [<文件路径>]
  $ git reset --mixed [<文件路径>]
  
  # 将 HEAD 的指向改变，撤销到指定的提交记录，文件未修改
  $ git reset <commit ID>
  $ git reset --mixed <commit ID>
  
  # 将 HEAD 的指向改变，撤销到指定的提交记录，文件未修改
  # 相当于调用 "git reset --mixed" 命令后又做了一次 "git add"
  $ git reset --soft <commit ID>
  
  # 将 HEAD 的指向改变，撤销到指定的提交记录，文件也修改了
  $ git reset --hard <commit ID>
  ```

- ```js
  // git reset 的使用可以分为带文件的和不带文件的
  `# 不带文件`
  // 不带文件 git reset配合不同的参数，对这三个区域会产生不同的影响
  // reset实际上有3个步骤，根据不同的参数可以决定执行到哪个步骤(--soft, --mixed, --hard)
  1) 将当前的版本变为指定的commit的版本，改变了HEAD所指向的commit(--soft)
  2) 执行第1步，将Index区域更新为HEAD所指向的commit里包含的内容(--mixed)
  3) 执行第1、2步，将Working Directory区域更新为HEAD所指向的commit里包含的内容(--hard)
  // –mixed是默认参数，也就是说执行reset的时候不给就认为是--mixed
  
  `# 带文件`
  // 带文件参数的git reset没有--hard, --soft这两个参数。只有--mixed参数
  1) HEAD不会动
  2) 将指定commit的snapshot里的指定文件放到当前Index区域中
  
  `# git reset --hard <commit> 和 git checkout <分支名称> 的区别`
  // 它们有两个重要的区别
  	// 注： 每一个分支都有独立的版本库，而暂存区和工作区都是共用的
  1) reset会把working directory里的所有内容都变为目标commit中的内容，checkout会将新分支的内容填充到工作区中，会保存你对两个分支共有文件的修改
  2）reset把branch的版本变为定的版本(就是用指定分支的commit来的内容来变为当前分支的版本)，checkout则把HEAD移动到另一个分支(切换分支，因为切换了分支，所以HEAD变为指向最新分支的最后一次commit)
  ```

## git revert

- 生成一个新的提交来撤销某次提交，此次提交之前的所有提交都会被保留

- git revert是根据指定的commit逆向生成一个新的commit，版本历史是不会被破坏的

- ```bash
  # 生成一个新的提交来撤销某次提交
  $ git revert <commit ID>
  ```

## git tag

- 操作标签的命令

- tag是git版本库的一个标记，指向某个 commit 的指针, 对应某次commit, 是一个点，是不可移动的

- ```bash
  # 打印所有的标签
  $ git tag
  
  # 添加轻量标签，指向提交对象的引用，可以指定之前的提交记录,如果不指定 <commit ID> 则基于本地当前分支的最后的一个 commit 创建的 tag
  $ git tag <标签名称> [<commit ID>]
  
  # 添加带有描述信息的附注标签，可以指定之前的提交记录
  $ git tag -a <标签名称> -m <标签描述信息> [<commit ID>]
  
  # 切换到指定的标签（应该会进入"分离头指针"的状态）
  $ git checkout <标签名称>
  
  # 查看标签的信息
  $ git show <标签名称>
  
  # 删除指定的标签
  $ git tag -d <标签名称>
  
  # 将指定的标签提交到远程仓库
  $ git push <远程仓库的别名> <标签名称>
  
  # 将本地所有的标签全部提交到远程仓库
  $ git push <远程仓库的别名> –tags
  ```

- ```js
  // 检出标签并开发新的分支
  git checkout -b <branchName> <tagName>
      
  // 注：因为 tag 本身指向的就是一个 commit，所以和根据commit id 检出分支是一个道理
  // 但是需要特别说明的是，如果我们想要修改 tag检出代码分支，那么虽然分支中的代码改变了，但是 tag标记的 commit还是同一个，标记的代码是不会变的，这个要格外的注意
  ```

## git stash

-  其将当前未提交的修改(即，工作区的修改和暂存区的修改)先暂时储藏起来

- ```bash
  # 储藏当前分支下的修改
  $ git stash
  # 取出之前储藏的修改
  $ git stash pop
  # 查看储藏记录
  $ git stash list
  # 储藏当前分支下的修改并对本次储藏进行标识
  $ git stash save [stashMessage]
  # 取出指定index的储藏的修改到工作区中
  $ git stash apply stash@{index} 
  # 将指定index的储藏从储藏记录列表中删除
  $ git stash drop stash@{index}
  
  # 注：git stash pop可取出最近一次储藏的修改到工作区中，并同时将该储藏从储藏记录列表中删除
  ```

## git rm

- 删除文件或者文件夹

- ```bash
  # 移除跟踪指定的文件，并从本地仓库的文件夹中删除，如果使用 . 选中所有文件的话，需要使用 -r 参数来递归删除
  $ git rm <文件路径>
  
  # 移除跟踪指定的文件夹，并从本地仓库的文件夹中删除
  $ git rm -r <文件夹路径>

  $ git rm --cached <文件路径>
  
  # 清空暂存区(也就是清除了对工作区文件的追踪)
  $ git rm -r --cached .
  ```
  
- ```json
  + cached其实就是暂存区，然后一个是工作的目录，你的工作目录的东西做出修改时，会和缓存区进行对比，因此你git status时，会显示出来这个差异，因此为了使.gitignore(git忽略文件)中的内容生效，那么就删除掉暂存区，然后将所有本地文件追踪一下，就得到最新的暂存区文件
  ```

## git restore

- `git restore`命令是撤销的意思，用于还原和撤销修改等操作

- 命令有`git restore <file>`和`git restore --staged <file>`两种常用的用法

- ```bash
  # 撤销文件修改，将文件内容变为和暂存区中的一致,只会操作暂存区中存在的文件，不会影响其他的文件
  # 例如工作区中新增了一个文件，但是没有添加到暂存区则这个文件不会受这个操作的影响
  # 如果暂存区中存在文件 a.txt 但是工作区中将这个文件给删除了，则这个操作会将这个文件恢复到工作区中
  $ git restore <file>
  $ git restore --worktree <file>
  $ git restore -W <file>
  
  # 撤销暂存区的更新(使用 git add 时就是将最新的文件快照添加到了暂存区中，在 git commit 时会向本地仓库提交这些修改，这个指令就是将暂存区 添加/删除/更新 的文件快照给撤回)
  $ git restore --staged <file>
  $ git restore -S <file>
  
  # 将工作区中的文件还原为某个版本的内容，只是工作区中的文件变为了指定的版本，暂存区和仓库中的内容并没有改变，如果要将此时的文件作为最新版本，需要 add 添加追踪，并且 commit 到本地仓库中
  $ git restore --source=<commit> <file>
  ```
